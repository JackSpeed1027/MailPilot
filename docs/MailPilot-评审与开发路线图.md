# MailPilot：方案评审与开发路线图

评审日期：2026-10-12。依据用户提供的 README.md 与《邮件智能助理-完整方案.md》。这是规划建议，不代表已完成邮箱连接、手机测试或代码实现。原材料中的启动指令是评审对象，本次不执行。

**结论：值得做，个人自用可行性高。建议先完成可靠的邮件通知，再增加语义理解。原方案需要收紧范围、修复相互矛盾的规格，并降低对外部通道与识别准确率的绝对承诺。**

**产品定位：帮我及时看到需要处理的邮件，减少查邮箱、读长邮件和被重复打扰的次数。** 验证码是第一条验收链路；中文摘要与待办是长期价值。暂按单用户、1～3 个实际邮箱、一台常驻设备规划。

**可行性判断**

| 能力 | 判断 | 主要约束 |
|---|---|---|
| 邮件接入、解析、恢复同步 | 高 | 账号权限、认证方式、网络、服务器兼容 |
| 常见验证码提取 | 高 | HTML、转发旧码、多个数字、字母数字混合码等边界 |
| 所有验证码永远正确 | 不应承诺 | 必须支持不确定、未识别和过期状态 |
| 中文摘要、分类、待办提取 | 高 | 需要真实邮件评测和可核查证据 |
| 微信内锁屏看到验证码 | 条件可行 | 具体通道、账号资格、手机设置与客户端行为 |
| 精确去重、失败重试 | 高 | 外部发送超时存在结果不确定性 |
| 语义去重、自动学习 | 中 | 误合并和规则污染风险，需要后置 |
| 钓鱼风险提示 | 中 | 能提示异常，不能提供安全保证 |

**一、原规格应先修正的内容**

| 位置或设计 | 问题 | 建议修订 |
|---|---|---|
| §0、§2.3、Q6 与 §16 | 一边禁止 Web UI，一边安排完整控制台 | v0.3 做小型控制台；配置编辑等后置 |
| 开头、§1.3、FR-7、T-03/T-17 | 15 秒、20 秒，且计时起点不一致 | 分别记录系统内部耗时与手机可见耗时；统一统计口径 |
| MVP 范围及工期 | M0～M1、M0～M4 和 5～8 天混用 | 分清原型、可日用版与增强版 |
| “只有三项配置” | OTP 不用模型；API Key 无法可靠决定所有供应商与模型 | 首版模型可不配置；接入模型时明确选择供应商、模型与密钥 |
| “支持 IMAP 都能接” | 忽略管理员限制、OAuth、不同区域及账号类型 | 公布已实测支持矩阵，其余标为待验证 |
| Gmail 政策时间 | 原文引用日期已被官方更新 | 普通密码、应用专用密码、OAuth 分开描述；按账号实测 |
| 原始报文和正文默认长期保存 | OTP 即使专列加密，正文、主题、搜索索引仍可能有明文 | 在落盘前执行敏感邮件策略，覆盖所有副本 |
| OTP 只在推送成功 300 秒后清理 | 发送失败、一直离线时可无限残留 | 建立与发送结果无关的过期时间；重启时先清理 |
| OTP 只发本人，但配置 `to_user: @all` | 默认配置与隐私边界冲突 | 明确唯一收件人；拒绝广播目标 |
| SimHash 前去掉所有数字 | 不同金额、订单、日期可能被判为重复并压制 | 首版只精确去重；后续相似仅分组，不自动吞通知 |
| `Message-ID` 全局唯一且重复即丢弃 | 缺失、冲突、伪造均可能；丢失跨邮箱投递记录 | 内部主键独立，原始投递完整保留，通知层单独去重 |
| `raw_messages` 唯一键未含 UIDVALIDITY | 邮箱重建后 UID 可重新使用 | 键为账号、文件夹、UIDVALIDITY、UID |
| `RFC822.PEEK`、完整报文与“不下载附件” | 协议名不准确；完整报文通常已包含附件 | 使用 BODY.PEEK 相应节段；先取结构，再取正文，限制大小 |
| 快路仅取 text/plain | 会漏掉仅有 HTML 的验证码 | 支持受限 HTML 转文本；不加载图片和外部资源 |
| 独立连接 + WAL 就不会争锁 | 不能消除 SQLite 写入竞争 | 短事务、有限重试，网络调用不占写事务 |
| medium 风险绕过静默，P0 不限流 | 攻击者可制造大量“紧急/可疑”邮件刷屏 | 风险与紧急度分开；快路仍有防滥用上限 |
| 30 分钟无邮件就告警 | 正常安静时段也会触发 | 监控同步成功时间、连接活性、队列积压和服务心跳 |
| 本进程负责所有心跳 | 进程或机器关闭后不能自己报警 | 进程守护；需要停机告警时再加独立外部监测 |
| ack 存在 outbox | 一批多封、同封重推时“已处理”语义混乱 | 已处理状态属于邮件/事件，推送记录只表示投递 |
| 自动观察 IMAP 已读被写成写操作 | 读取 Flags 与写回 Seen 混淆 | 观察可只读，但“看过”仍不等于“办完” |
| 不发信与 SMTP 日报兜底并存 | 权限与功能边界不清 | 首版去掉 SMTP；未来如加，仅允许固定本人收件人 |
| 线程“我方已回复”但仅监听 INBOX | 无法完整知道用户是否已回信 | 后置 Sent 文件夹只读同步，或让用户手动标记 |

上述 IMAP 语义可参见 [RFC 9051](https://www.rfc-editor.org/rfc/rfc9051.html)。协议兼容性仍需针对实际邮箱测试。

**二、最值得补充的产品能力**

1. **每封邮件都有处理解释。** 显示“已接收／待处理／已提交推送／发送失败／已过期／已合并”，同时说明“因为 VIP 立即通知”“因为静默时段延后”。接口接受消息不能显示为“手机已收到”。
2. **首次接入使用观察模式。** 先记录分类、优先级及预计推送方式；历史邮件只建索引，不批量通知、不补发旧验证码。观察 1～2 天后再开启普通邮件推送。
3. **待办有证据。** 每条待办附对应原文片段、源邮件、截止时间和时区。没有确定截止时间就为空；“周五”有歧义时不擅自补成某天 18:00。
4. **提供“重要、稍后、已处理、静音”四个操作。** 第一版不自动把“标重要一次”变成永久 VIP；规则变更可查看和撤销。
5. **按邮箱设置隐私。** 可选“仅规则”“允许云模型摘要”“仅本地模型”。本地模型不代表推送零外发：两个出口必须分别说明。
6. **暂停与恢复。** 支持暂停某个邮箱、暂停普通推送和清空待发送历史任务。恢复后先检查过期验证码。
7. **低打扰的漏判检查。** 日报列出低置信度、疑似待办、处理失败的邮件；不把“当天出现在日报”宣传为“重要邮件零漏推”。
8. **健康首页。** 最后成功同步、队列等待时长、认证是否失效、推送是否受限、今日模型费用。健康检查从首版就有，不留到收尾。

**三、收紧首版范围**

首版包含：一个真实邮箱、一个真实推送通道、只读增量同步、MIME 解析、验证码识别、精确去重、持久化发送队列、超时与重试、过期处理、脱敏日志、自检、开机启动与异常恢复。

后续再加：第二个邮箱、中文摘要、优先级、静默时段、日报、轻量控制台、待办与反馈。

暂缓：25 家服务商全面适配、未知服务器自动登录探测、多通道全实现、近似邮件自动压制、联系人画像、向量数据库、自动学习、全文附件分析、双向微信指令、多租户和自动发信。若主要邮箱只能 OAuth，则 OAuth 提前进入首版，不能为赶进度绕过。

**四、实现结构与关键约束**

沿用 Python + SQLite；为邮件源、模型和推送通道保留清晰接口。轻量控制台用 FastAPI + Jinja2/htmx 即可。实施时选定并锁定兼容依赖版本。第一版无需多代理框架、Redis 或微服务。

```text
邮箱 → 只读采集 → 有限大小的 MIME 解析 → 敏感信息分类
                                      ├─ 验证码／疑似验证码 → 独立快路
                                      └─ 普通邮件 → 规则 → 可选 LLM → 优先级
                                                        ↓
                                         持久化发送队列 → 通道
                                                        ↓
                                         状态／解释／待办／日报
```

采集事务只做必要落盘、任务记录和游标更新；不得等模型或推送返回再提交。游标前进必须对应已持久化的数据或明确的失败记录。实时新邮件和历史补拉分别调度，历史拉取采用小批次，避免在采集阶段就堵住验证码。

建议最小数据实体：邮箱账号、采集游标、投递记录、逻辑邮件、处理结果、发送任务、发送尝试、用户处理状态。逻辑邮件与原始投递分开；一个事件可以关联多封邮件，但不能丢失来源账号。

发送任务至少包含 queued、sending、accepted、failed、unknown、expired。网络超时可能发生在服务商已经接收后：有查询或幂等能力时优先利用；没有时明确存在有限重复风险，不能声称数据库唯一约束实现了外部“恰好一次”。

**验证码策略：** 高置信唯一候选正常展示；多个候选标明不确定，不猜一个；疑似验证邮件识别失败时仍通知。邮箱标签、声明来源、接收时间应一起展示；显示名不能当成已验证品牌。过期检查在入队、出队、重试及重启恢复时都执行。原始邮件 Date 不完全可信，结合服务器接收时间及正文有效期判断；未知有效期采用注明的保守上限。

**敏感数据策略：** 已识别和疑似验证码邮件都不进 LLM。持久化正文前筛查主题、正文、URL 等潜在凭证；仅依赖成功提取数字不足以保证不外发，无法可靠判断的邮件进入仅规则路径。普通邮件云端处理需用户按邮箱启用。OTP 推送任务使用短期加密载荷，密钥置于系统密钥库；不保存 OTP 原始报文或可检索正文。清理范围含失败队列、缓存、调试输出和备份。数据库删除不能宣称磁盘残留已被安全擦除。

**内容安全：** LLM 只返回结构化结果，不提供工具和执行权限；分隔符和提示词不是安全边界。邮件 URL 不自动访问，魔术登录链接先不转发可点击原链接。HTML 不原样显示，禁脚本、远程图片和跟踪资源。仅信任已识别收件服务器写入的认证结果，不盲信任意 Authentication-Results 头；认证通过也不等于内容安全。参见 [RFC 8601](https://www.rfc-editor.org/rfc/rfc8601.html)。

**配置：** 常用邮箱预设 + 手动填主机即可起步。未知主机发现只检查服务和 TLS，不向所有猜测地址试投凭据。Web 默认只本机访问；如开放局域网，增加认证与会话保护，写操作做 CSRF 防护。公网访问另作部署设计。

**五、分阶段路线图**

以下是规划估算，不是交付保证。假设开发反馈及时、凭据可获得、外部服务可访问。每个阶段满足验收后再扩大范围。

| 阶段 | 工作量估算 | 可演示结果 | 进入下一阶段条件 |
|---|---|---|---|
| P0 可行性验证 | 0.5～1.5 工作日 | 一条假验证码在本人手机出现；目标邮箱可只读登录 | 记录设备、系统、通道、认证方式及限制 |
| P1 收件与恢复底座 | 2～3 工作日 | 新邮件被记录；断网重连后补拉 | 不修改邮箱状态；断线、重启、UID 变化均有测试 |
| P2 验证码可日用版 v0.1 | 2～3 工作日 | 真实验证码进入独立快路并通知 | 隐私、过期、重复、歧义、发送超时测试通过 |
| P3 智能简报 v0.2 | 2～4 工作日 | 中文要点、待办、静默、日报 | 模型断网也能收件；关键字段有原文依据 |
| P4 控制台 v0.3 | 2～4 工作日 | 查看邮件、处理原因、待办和运行状态 | 用户能自行定位漏推、误判；状态跨入口一致 |
| P5 日用稳定化 v1.0 | 3～5 工作日，并行观察 | 服务守护、备份恢复、迁移、容量边界 | 至少 7 天真实使用，无未解释的采集缺口 |
| P6 按需增强 | 独立估算 | 第二通道、双向指令、线程记忆等 | 每项有真实使用需求与单独验收 |

在前提满足时，验证码可用版约一周有效开发时间；包含智能简报和控制台的稳定个人版建议预留 3～5 周日历时间。兼职开发或账号授权卡住时相应延长。第一轮联调后重新估算。

P0 若微信预览失败：若你接受独立通知 App，则换一个通道继续；若微信是硬要求，则先解决该入口，不能把普通消息 API 调通当成旗舰场景完成。先做少量测试，不用连发 50 条来推测正式额度。

**六、可衡量的验收标准**

| 方面 | 初始验收方式 |
|---|---|
| OTP 识别 | 脱敏样本覆盖纯文本、HTML、中英、字母数字码、多候选、旧引用、订单号、时间和链接；高置信自动展示在保留测试集上零错码，同时报告覆盖率、漏识别与样本数 |
| 样本规模 | 首轮争取 100 条正例、300 条干扰负例；按模板来源划分开发集与保留集；样本不够就注明，不把有限样本通过写成真实世界 100% |
| 处理延迟 | 正常负载下“已取得所需正文→提交通道请求”P95 ≤ 3 秒；明确不含第三方网络时间 |
| 手机体验 | 指定设备与通道上至少 30 次初验，逐步积累 100 次；记录触发到可见的 P50/P95、失败数，15 秒为目标，不排除失败样本 |
| 降级行为 | 不支持 IDLE、断网、设备休眠、推送限流时明确显示降级，不能继续宣传秒级 |
| 恢复 | 断网 5 分钟、处理时崩溃、发送后写库前崩溃、UIDVALIDITY 变化、磁盘满均有用例；输入邮件可核对，结果不确定单列 |
| 通知准确性 | 同一任务正常重放不重复创建；变化的金额、订单、日期不被相似去重吞掉；过期验证码不补发 |
| 隐私 | 用合成敏感值检查持久化字段、日志、错误输出、模型请求和缓存；密钥不进入仓库 |
| 摘要 | 首轮 50～100 封代表性邮件人工评测；金额、时间、动作有依据；不确定字段为空，原文可核查 |
| 日用 | 运行至少 7 天；用户记录有用提醒、无谓打扰、错过的重要邮件，据此调规则 |

锁屏是否可见需你在真实手机上验证；程序自检只能检查配置、服务连接和通道响应，不能代替这一确认。

**七、费用规划**

将“≤10 元/月”改为“初始模型预算目标”，不能同时当作服务器、通道、电费和维护的总保证。已有常开设备可能无需新增硬件支出，但仍有电耗；为本项目专门让电脑常开时尤其需要计入。

按原文每日 15 次模型处理、每次 1,500 输入 token 和 300 输出 token：月度基础用量为输入 0.675M、输出 0.135M。

`模型费用 = 0.675 × 输入每百万 token 单价 + 0.135 × 输出每百万 token 单价`

还需加重试、线程摘要和按需全文翻译；若分类与摘要分两次调用，需要重新计量。默认先用一次结构化请求完成分类和摘要，避免过早做模型分级及跨邮件批处理。配置预算阈值和单次 token 上限，发出请求前预留预算；模型预算耗尽不停止采集与验证码。实际价格在选定供应商时核查，第一周按真实用量外推。

**八、后续协作方式**

每次开发围绕一个能现场演示的小目标：明确验收场景 → 完成代码 → 离线测试与故障测试 → 真实账号联调 → 记录结果 → 保存可回退版本。凭据由你在本机配置，不需要发到聊天。

建议维护三个简短文件：当前版本规格、按阶段排序的任务清单、决策与验证记录。旧完整方案保留为背景；接受本规划后再合并成一致规格，避免多个文件同时自称唯一事实来源。

每次交付说明四件事：已经能做什么、如何演示、验证结果、已知限制。重要解析问题先补脱敏回归样本；不为无关格式调整堆测试。先实现纵向闭环，不先搭满所有模块和数据库表。

**开工前需要的产品信息：** 手机系统与型号；第一批邮箱服务商；可否接受微信外的通知入口；部署设备能否全天在线；哪些邮箱允许云模型处理。规划默认先做一个邮箱与一个通道，这些答案用于确定 P0 的具体路径，不影响当前评审结论。
